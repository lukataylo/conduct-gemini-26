Aperture UI Surfaces

Every screen the access-scope agent needs, with three or four ways to build each one, what each costs on a one-day clock, and which to pick for a demo at 20:00. Aperture is a working codename — an opening sized to what you're allowed to see.

Revised after three independent reviews (design, red-team, judge). The one beat to protect: close the project and the tool vanishes from the coding agent's session. Everything else is core or cut.

What the research says, and what we do about it

Two threads: how the industry builds generative UI, and how access-governance products fail their users. Each finding ends with the design consequence.

Generative UI

The field converged on JSON spec + fixed component catalog, not model-written code. Vercel's AI SDK abandoned streaming React Server Components for schema-validated JSON; OpenAI's Apps SDK sandboxes components in an iframe; Google's A2UI protocol (co-built with the Gemini Enterprise team) calls it "least-privilege UI": the agent sends data, never code.

Our registry pattern is the right one. Make Gemini speak A2UI on a DeepMind-hosted stage.

The sharpest named risk is a generated element triggering a privileged action because the UI showed it. The fix is a constraint validator: every action re-checked server-side at execution time.

Buttons carry action ids, never parameters the server trusts. Policy runs twice: at proposal and at execution.

Full regeneration flickers and loses scroll, open panels and typed input. Incremental patching of a panel list is the documented remedy. Hallucinated component names are universal; the mitigation is a visible non-crashing fallback.

Diff panel ids, animate add/remove, stream data separately from layout. Keep UnknownComponent.

Generated UI can't be evaluated like text; teams snapshot-test the catalog instead. Unsupervised generation has produced accessibility failures and buried "deny" buttons.

Test the registry, not the generation. The approver's deny control is never model-positioned.

Almost every generative-UI case study is chat-first. Admin and dashboard surfaces are thin.

Say so on stage: this is generative UI for an access-control console, not a chatbot.

Access governance

Approval fatigue is the dominant failure: reviewers approve over 95% of entitlements in under ten seconds because the card shows CN=Finance_RW_102 and a deadline, and nothing else.

The approval card carries the agent's reasoning, tier, who else holds it, and a proposed expiry — inline, not a click away.

Uniform approval paths cause fatigue by training people to click through everything the same way. The fix is tiering: auto-approve the routine, escalate only the ambiguous, add friction only at the top.

Our tiered engine is the industry pattern. Critical-tier approvals require a typed justification.

Standing privilege — access nobody revoked when the project ended — is the top finding in access audits and a leading breach vector, distinct from orphaned access after offboarding.

Every grant has an expiry by construction. "Close project" revokes in bulk. Both are demo beats.

No vendor's flagship surface is a portal any more: ConductorOne, Opal, P0, Britive, Apono and Entitle all put approve/deny inside Slack or the terminal because that's where approvers are.

The in-app queue stays (decided), styled as the chat-card pattern people already trust.

Audit logs are judged on how usable they are during an incident, not on completeness. Agent-as-requester is a barely-served category — only P0 targets it.

Per-request story timelines. And the differentiator: the requester in our demo is a coding agent.

The one rule every surface obeys

Models propose and explain. A deterministic engine decides. A fixed catalog constrains what can render. This is the security answer, the demo narrative, and the reason five people can build in parallel.

Gemini Proposes Parses the task into an AccessRequest with resource ids constrained to a known enum. Composes the A2UI layout. Writes the reasoning an approver reads.
Policy engine Decides Pure functions over typed input: tier × duration × team → grant, escalate, deny. Re-run at execution time for every action id a generated button carries.
Renderer Constrains Only catalog components render. Unknown names fall back visibly. The deny control is fixed in place, never model-positioned.
Audit Remembers Every transition is a typed AuditEvent, hash-chained, with the Logfire trace of the model call it came from.

Surface 2

Requester dashboard — the generative UI itself

Show exactly the tools this person's grants cover, right now, and nothing else. The question is how much of the layout the model composes and how changes arrive.

track 1A2UISSE
A

A2UI generation with incremental patching

Recommended

On each scope change Gemini emits an A2UI message — a component tree against our catalog plus a separate data model. The client diffs on panel.id (now in the schema), animates adds and removes, and streams data-model updates over SSE without regenerating layout. After generation the server drops any panel whose grant or case id isn't in the viewer's own active set.

For
  • Google's own protocol, in front of DeepMind
  • No flicker: layout is generated once per scope change, data streams continuously
  • Schema validation rejects anything off-catalog before render
Against
  • Only earns its name with a catalog wide enough that composition differs from the fallback — pair it with B or don't build it
  • Prompt needs tuning so the layout is stable across calls
cost M–Ldemo risk medium
B

Role-adaptive composition

Stretch · second wow

Same data, different composition per viewer: an intern with two grants gets a focused two-panel view; an approver gets queue-first; an auditor gets timeline-first. The model chooses grouping, order and density from scope size and role.

For
  • The strongest visual proof that the UI is generated from scope — "your version is specific to you"
  • Builds on A, no new plumbing
Against
  • Three prompt variants to tune and QA
  • If layouts differ too much, the audience loses orientation
cost M on top of Ademo risk medium
C

Static shell, state-driven panels

Fallback · already built

What's in the repo now: /ui-spec maps grants and cases to panels deterministically; the client polls and renders through the registry.

For
  • Works today; no flicker by construction
  • Deterministic, easy to test
Against
  • Generative in name only — a judge will ask where the model is
  • Polling looks laggy next to a stream
cost donedemo risk low
D

Full regeneration every change

Avoid

Gemini re-emits the entire spec on every event; the client replaces the tree wholesale.

For
  • Simplest possible loop
Against
  • The documented flicker-and-lost-state failure
  • One model round-trip per event, on stage, over venue wifi
cost Sdemo risk high
Surface 3

The agent's surface — a scoped tool manifest

For a coding agent, the UI is its tool list. The requester's agent should see exactly and only the tools its current grants allow, and lose them the moment a grant is revoked. This is the surface no competitor has, the one that makes the closing beat land, and — after review — the spine of track 2 from noon, hosted on Modal, with computer use demoted to the stretch layer.

track 2track 5 · /grantsMCP on Modal
A

Per-requester MCP server derived from grants

Recommended

tools/list is computed from GET /grants?requester_id= (active and unexpired): a bucket grant yields gcs_list_objects and gcs_read_object; a dataset grant yields bq_query. Every tool handler re-checks the grant before acting and logs ACTION_EXECUTED — this is where "policy runs twice" is true. Revocation emits tools/list_changed and the tool is gone mid-session. Each requester's server presents a bearer token issued at seed time, so a client can't pick the manager's tools by changing an id. Claude Code on the presenter's laptop is the client.

For
  • Least-privilege UI in the literal sense
  • Revocation becomes visible to the agent instantly — the strongest possible "access removed when the project is over"
  • A category only P0 is chasing; Modal earns its place hosting it even if computer use is cut
Against
  • An MCP server plus a live client on stage
  • Tools need mock implementations against the fake GCP layer
cost Mdemo risk medium
B

Add-on

For
  • Cheap; one prompt per grant

Against
  • Cosmetic without A
cost Sdemo risk low

Surface 4

Approval queue

Get a manager to make a real decision in the time they'd otherwise spend rubber-stamping. The card is the product.

A

Recommended

Surface 7

Agent in action — computer use

An agent operating the console to enact a grant that was already decided. Never deciding, only executing. After review this is the stretch layer, not the spine: it's the flashiest beat and the least connected to the thesis, and a Modal Sandbox can't reach localhost, so the console needs a public URL first. The answer to "you have an API, why is an agent clicking?": the console stands in for every enterprise system that has no API — Conduct's world. The engine decides; the agent enacts where only a UI exists; the ACTION_EXECUTED event proves it did.

Hardening before the demo

From the red-team pass. The first group is on main; the second is owed before 18:45. Anyone on venue wifi with the Railway URL is a threat model tonight.

Done

Request ids are server-assigned; a re-POST can't swap the requester on an escalated case. The case snapshots requester and duration at open time and grants from the snapshot.

The requester is looked up by id; posted team and manager_id are ignored, so cross-team checks can't be bypassed by self-assertion.

Votes are accepted only from the case's required approvers, in both the engine and the endpoint.

Every reader of grants filters on expiry, not just revoked. Audit ids, timestamps and prev_hash are stamped on ingest; /audit/verify reports the first broken index.

Registry lookup uses Object.hasOwn — a generated name like constructor falls back instead of resolving through the prototype. A per-panel error boundary keeps one bad panel from blanking the dashboard.

Owed today

Identity is a header tonight. X-Demo-Key middleware on every write; X-Actor set by the role picker must match approver_id on votes. Say on stage: "this is the line SSO sits behind."

MCP bearer tokens. One per requester at seed time; the server presents it on /grants. A client can't pick the manager's tools by changing an id.

Tool handlers re-check. Active, unexpired, resource matches — then act, then ACTION_EXECUTED. This is the only place "policy runs twice" is true; don't claim more.

Requester text is a claim. Rendered only in a labelled, quoted, truncated block on the card. Never in the summary or compose prompts. Not in REQUEST_RECEIVED.detail (already moved to payload).

Generated specs are filtered. Drop any panel whose grant or case id isn't in the viewer's own active set. Approve and deny are static chrome, never catalog entries.

Chaining over the effective set. Active grants plus requested, against a short toxic-pairs list — a split request or a second requester doesn't help.

Audit ingest is authenticated. ACTION_EXECUTED requires the runtime's secret; the chain head goes into a Logfire span every N events as an anchor. Restrict CORS to the deployed UI origin.

Computer use is fenced. Goal from the Grant only, turn budget, egress limited to the console URL, post-run diff or revert.

What a judge will poke at

Pre-empted answers, rewritten to claim only what the code guarantees. Each one points at something on screen.

Where is the model actually deciding?

It isn't. Gemini parses and composes; the engine decides with pure functions you can read. Here's the reason string, here's the Logfire span with the model's raw output next to it.

What stops a generated button from doing something it shouldn't?

Generated panels are display-only; approve and deny are static chrome outside the generated tree. Policy is re-checked where it matters: every MCP tool call verifies the grant is active and unexpired before acting. And here's an off-catalog name rendering as a visible fallback, not a control.

Isn't this an approval workflow with a chatbot on top?

Watch the coding agent's tool list. Close the project — the tool is gone from its session in the same second the panel leaves the dashboard. Every grant expires and the sweeper enforces it; standing privilege is the number-one audit finding and here it has a deadline by construction.

Prompt injection through the task description?

Resource ids are an enum in the response schema. The summary prompt sees only the typed decision. The requester's words appear on the card in a quoted block labelled unverified — a claim the approver reads, not a fact the system asserts.

Two individually-fine grants that combine into an exfiltration path?

Only once built: the engine checks the requester's effective set — what they'd hold, not what they asked for — against named toxic combinations, so splitting the request doesn't help. That's the second scenario.

You have an API. Why is an agent clicking through a console?

The console stands in for every enterprise system that has no API. The engine decides; the agent enacts where only a UI exists; the ACTION_EXECUTED event and its screenshot prove it did. Nothing is decided in the console.

Is the computer-use live?

Whichever is true. If replay: "recorded at 16:40 in a Modal Sandbox, here's the trace." If live: it passed rehearsal twice at 18:30. If cut: "the tool call you just watched is the enactment; the console is next."

Who can vote or revoke right now?

Tonight, anyone holding the demo key and the actor header the role picker sets. That header is the line SSO sits behind; the engine and the audit chain don't change when it does.
