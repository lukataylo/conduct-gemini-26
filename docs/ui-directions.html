Aperture UI Directions

Four ways the product could look, each drawn as a working mockup on the same Atlas scenario — Alex Chen's coding agent asks for a bucket and a dataset; Priya and Jordan decide; the project closes. Pick one, or the recommended blend at the end.

What the field looks like

From a screen-level survey of ConductorOne, Opal, Teleport, P0, Britive, Apono, Entitle, Okta IGA and Google Cloud PAM, plus shipped generative UIs (A2UI, OpenAI Apps SDK, CopilotKit, Vercel AI SDK, Thesys C1).

Everyone does this

  • Request = resource + duration picker (presets, capped by a max) + justification. Opal adds "expire when the ticket closes".
  • Approver = a chat card: requester, resource, duration, justification. Approve on the right, Reject on the left, a reason popup on either (Apono, Entitle, P0). P0 lets the approver set the duration.
  • My access = a table with a status label and time remaining, plus Revoke / Check in / Relinquish (Britive's library-checkout metaphor; PAM's twelve state labels).
  • Two buckets: Active vs Pending (P0, PAM tabs, Britive filters). Teleport adds a persistent "elevated" banner with Switch back.
  • Audit = a flat activity table filtered by request or user.
  • Generated UI: host owns the chrome, the agent fills a well; skeletons carry request context; catalogs are ~15 components; values stream into an already-rendered tree.

Nobody does this

  • Shows the system's reason for escalating, the tier, or "who else on your team holds this" — every card shows only the requester's justification.
  • Shows the agent's own view: its scoped tool list, and that list shrinking on revoke.
  • A per-request story with verification (chain OK / broken).
  • A dashboard that visibly re-composes when scope changes — grants are rows that appear; nothing else moves.
  • Denial as a next step — "request the narrower version".
  • A "composed for you" affordance — no shipped generative UI labels what the agent made versus what's fixed.

Four directions

Direction A

Console

Borrow the shape every judge has used — sidebar, tabs, a table with status labels and time remaining — and confine the generated part to one labelled strip above the table. The dashboard doesn't re-compose; rows appear.

Direction B

Feed

Every event is a card in one stream — the agent's request, the engine's decision, the approver's card with Reject left and Approve right, the tool-list change. A "Now" rail on the right keeps current state visible so it never degrades into a transcript.

BorrowsApono / Entitle / P0 Slack cards; Vercel and A2UI chat-adjacent cards; Opal's comment thread
Trades awayReads as a chatbot to a skeptical judge; layout can't visibly re-compose
Cost tonightS — one card component, one stream
Best beatThe approval, inline, with the engine's reason right above the buttons

Direction C

Aperture

The scope is the picture. An iris at the top opens a wedge per grant and closes it on revoke; a diff ribbon says what changed and when it was composed. Left column is static chrome — identity, the request box, approve and deny. Right column is the generated well, labelled as such. Flip it to the agent's view and the same panels become tool rows.

BorrowsHost-chrome / agent-well split (Apps SDK, CopilotKit); Thesys per-user composition; Teleport's elevated state; P0's relinquish
Trades awayFamiliarity — the iris has to earn itself in five seconds; more CSS than A or B
Cost tonightM — the well is the existing registry; the iris is one SVG; the ribbon is a diff of panel ids
Best beatClose project: wedges close, panels fade, tools strike through, ribbon shows the minus — one frame

Recommendation: C, with D inside it and B's card anatomy

Build direction C as the app. Its right column is already the registry renderer in the repo; add the label, the ribbon (a diff of panel ids over SSE), and the iris (one SVG with a wedge per grant). Put D's proof terminal and tool list behind C's "Agent view" toggle so the closing beat shows panel, wedge, tool row and gcloud all changing in the same second. Use B's card anatomy — reason and peers directly above Reject-left / Approve-right — for the approver screen, since it's the shape approvers already trust. Keep A's table as the audit and grants fallback: it's what /audit and /grants already return.

Build order for track 1: SSE consumer → approver screen (B's card) → C's two-column shell with the label → ribbon → iris → agent-view toggle → the close-project animation. The iris and the animation are the only parts that aren't already data on the wire.
